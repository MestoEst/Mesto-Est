# Один набор мест: GeoJSON → Django → API → карта

Основной контролируемый набор: **main/data/spots.geojson**, dataset=`canonical-v1`. Он содержит 734 места в 66 зонах, однократно экспортированные из карты Ани с уже сохранёнными ID. Сопоставление со спутниковыми полигонами отменено; подтверждать прежние 300 пар не требуется.

## Что является источником

GeoJSON служит для контролируемой первоначальной загрузки и обновлений. При каждом обычном запуске карта получает **весь набор и статусы из GET /api/spots/**. Генератор RUNS не подключается, localStorage не подменяет места. Нет скрытого резервного набора: ошибка/пустой ответ API показывают сообщение с кнопкой «Повторить загрузку».

Исходный спутниковый файл сохранён без изменений в main/data/archive/spots-satellite-original.geojson. Снимки генератора сохранены там же только для воспроизведения экспорта; они не входят в приложение. Отчёты о сопоставлении перенесены в docs/spot-ids/archive и помечены архивными. Команда remap_spot_codes теперь отклоняет запуск: старую историю нельзя переносить по той таблице.

## Геометрия и оформление

Физическая граница — Feature.geometry (Polygon) канонического файла, затем ParkingSpot.geometry и тот же Polygon в API. Она получена из центров, фактической ориентации и номинальных размеров прежнего генератора. Это модель карты Ани, а не новое геодезическое измерение.

В прежнем makeBays половина ширины умножалась на 0.46 вместо 0.5: это 8%-й отступ разметки. Экспорт убирает **только этот отступ** из физических границ. При рисовании displayPolygon применяет его обратно в отдельный b.poly, затем SPOTS рисует дополнительные слоты/обводки и машинки. Ни машинки, ни GAP_M, ни толщина обводки не записаны как физические границы.

Все 734 отображаемых полигона и центры проверены против исходной карты с допуском 1e-12 градуса. Сохранена фактическая ориентация, в том числе существовавшее поведение одиночных мест; экспорт не исправляет их по предположениям.

Однократный экспорт воспроизводится командой `node tools/export_canonical_initial.cjs work/reexport.geojson`. Она требует новый файл и не перезаписывает основной. Это проверка происхождения данных, не способ повседневного редактирования. Результат сравнен побайтно с первоначальным каноническим файлом.

## ID, зона, номер и порядок

- properties.id ↔ ParkingSpot.code ↔ properties.id API: постоянный ID места. Значения вида z1:0 сохранены, но префикс больше не определяет зону.
- properties.zone ↔ ParkingSpot.zone (FK ParkingZone): явная принадлежность зоне. Старый block сохранён как совместимый псевдоним.
- display_number: отображаемый номер. display_order: порядок интерфейса. Это отдельные сохраняемые поля у места и зоны.
- row_id: сохранённая группа для декоративной подложки ряда; не участвует в выдаче ID.

Начальный порядок зон задан по центрам с севера на юг (latitude убывает), затем с запада на восток (longitude возрастает), с ID как разрешением точного равенства. В каждой зоне аналогично упорядочены центры мест. Номера и порядок записаны один раз. При следующих загрузках сортировка идёт по сохранённым display_order, а не пересчитывается по координатам. Перемещение, смена зоны и перенумерация не меняют ID.

Для нового места выполните `python manage.py new_spot_id`: команда резервирует UUID в SpotIdentity. Добавьте новый Feature с этим ID, Polygon, существующей zone, свободными display_number/display_order и row_id. Сначала проверьте --dry-run, затем импортируйте. Для изменения существующего места отредактируйте геометрию/зону/номер, **сохранив id**. При переносе в другую зону проверьте свободный номер и порядок. Для новой зоны добавьте запись в zones.

Реестр SpotIdentity не очищается. Для вывода места из эксплуатации: `python manage.py retire_spot '<id>' --dry-run`, затем та же команда без --dry-run; после этого удалите Feature из будущего файла обновлений. Место и его история остаются в БД с is_active=False. Возвращать его ID другому физическому месту нельзя. Импорт откажет даже после ручного удаления ParkingSpot, если ID уже помечен used в реестре.

## Импорт и API

GeoJSON содержит type=FeatureCollection, dataset=canonical-v1, zones и features. Перед записью целиком проверяются ID, номера/порядок, Polygon, диапазоны координат, замкнутость и корректность колец и ссылки на зоны. Также проверяются конфликты с сохраняемыми записями БД. Все записи выполняются в transaction.atomic(). Повторный импорт обновляет те же PK. Статусы, наблюдения и статистика при обновлении геометрии не сбрасываются.

**Отсутствие Feature не удаляет и не деактивирует запись.** Это защита от неполного файла, а не команда удаления. Для вывода места используйте retire_spot. Аналогично сохраняются зоны, не перечисленные в обновлении.

GET /api/spots/ возвращает только активные canonical-v1, вместе с zones, display_number/display_order, row_id, is_occupied и статистикой. id/zone — основные поля; code/block — совместимые псевдонимы. Обратный импорт ответа API поддержан; импорт не принимает из ответа текущий статус как команду изменения истории.

POST /api/spots/<id>/status/ с {"is_occupied":true/false} изменяет только активное каноническое место с этим ID. В транзакции сохраняются статус, SpotObservation и SpotHourStat. Архивное место с совпадающим code не затрагивается. Выбор на карте, список мест, форма «Сдать» и отметки используют ID; индекс используется только как временный доступ к текущему массиву для рисования.

Статус null означает **неизвестно**: серое место, без машинки. Счётчики раздельно показывают free/busy/unknown; неизвестные не считаются свободными. Демо-движение отключено для реальных данных. Прежний случайный прогноз не применяется. Зонная отметка — отдельное действие и не записывает статусы всех мест; имеющийся зонный API в этом репозитории не реализован, флаг marks остаётся false, зонные отметки пока локальны. Примерные объявления и точки зарядок/спецмест сохранены как прежние демонстрационные сведения, отдельно от физических полигонов; backend объявлений/броней не добавлялся.

Отметка места сохраняется на сервере; при ошибке записи интерфейс возвращает прежний статус. Повторные нажатия блокируются до ответа. «Отменить» для известного прежнего статуса записывает противоположное наблюдение, не удаляя историю. Для неизвестного прежнего статуса эта кнопка не предлагается, поскольку endpoint принимает только true/false.

## Старый localStorage и редактор

Данные me_map_v2 и существующая me_map_v2_before_ids сохранены. Если копии ещё нет, приложение создаёт её, не изменяя исходник. Старая разметка не читается как источник мест. При наличии данных показывается сообщение и кнопка экспорта полного исходного JSON. Полученный файл не импортируется автоматически. Содержимое браузера пользователя недоступно из репозитория; сравнение с ним возможно только после экспорта. В браузерной проверке подставлялась тестовая старая разметка: она не перекрыла API и не изменила существующую резервную копию.

Работающего редактора геометрии в актуальном репозитории нет (кнопка скрыта). Новое сохранение геометрии выполняется через проверенный GeoJSON и команду импорта; скрытого второго сохранения в браузере нет.

## Проверки на временной базе

```sh
python -m venv .venv
.venv/bin/pip install -r requirements.txt
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python manage.py test main
node tests/spot_ids.test.cjs
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python tools/rehearse_spot_ids.py
```

В Windows вместо .venv/bin/python используйте .venv\Scripts\python. Для JS нужен Node. Тестировалось: Python 3.12, Django 6.1.3, Shapely 2.2.0, Node 24.

rehearse_spot_ids.py **сам создаёт отдельную временную SQLite**, выполняет миграции и затем удаляет её. Проверены 735 старых мест (включая намеренное совпадение code), 734 новых, сохранение всех старых PK/наблюдений/статистики и пользователя/профиля, реальная связанная тестовая бронь как блокировка, полная SQLite-копия, повторный импорт, откат сбоя перехода. Рабочая база не открывается.

Для самостоятельной браузерной проверки создайте отдельную базу; не запускайте browser_spots.cjs против рабочей базы — тест меняет статусы:

```sh
mkdir -p work
export MESTO_DB_PATH="$PWD/work/browser-check.sqlite3"
.venv/bin/python manage.py migrate --noinput
.venv/bin/python manage.py import_spots main/data/spots.geojson
.venv/bin/python manage.py runserver 127.0.0.1:8765 --noreload
# Во втором терминале:
npm install
SPOT_TEST_URL=http://127.0.0.1:8765 CHROMIUM_PATH=/usr/bin/chromium npm run test:browser
```

Путь Chromium укажите для своей системы. При использовании браузера Playwright вместо системного установите `npx playwright install chromium` и передайте исполняемый файл либо измените CHROMIUM_PATH. В текущем окружении использовался /usr/bin/chromium. Скриншоты теста: work/browser/. Проверены Leaflet Canvas, выбор полигона, размеры/расположение, машинки, подписи/подсветка, сохранение статуса после reload, соседнее место, счётчики неизвестных, rollback ошибки POST, отдельное зонное действие, форма «Сдать», изоляция localStorage и фактическое скачивание его экспорта, мобильная компоновка, ошибка GET и повторная загрузка. Скриншоты просмотрены. Leaflet 1.9.4 с лицензией включён локально, чтобы недоступность CDN не отключала карту. Карта проверялась с ?map=flat; доступность внешних OSM-плиток не является проверкой данных мест.

## Процедура перехода рабочей SQLite — только вручную

Ниже команды **изменяют выбранную базу**. Сначала отрепетируйте на копии, остановите сервер и фоновые записи. Не запускайте прежний remap_spot_codes и не сбрасывайте базу. Перед migrate нужна полная копия старой схемы; transition создаст дополнительную копию уже обновлённой схемы перед переключением данных. Для каждой копии используйте новый путь.

```sh
mkdir -p backups
python tools/backup_sqlite.py --source /absolute/path/db.sqlite3 --output backups/before-schema.sqlite3
export MESTO_DB_PATH=/absolute/path/db.sqlite3
python manage.py migrate --noinput
python manage.py transition_spots main/data/spots.geojson --dry-run
python manage.py transition_spots main/data/spots.geojson --backup backups/before-dataset-switch.sqlite3
python manage.py import_spots main/data/spots.geojson --dry-run
python manage.py import_spots main/data/spots.geojson
```

Что меняется:

1. backup_sqlite.py создаёт полную согласованную копию и проверяет integrity_check; исходник открывается read-only.
2. migrate добавляет поля/таблицы. Все существовавшие ParkingSpot получают dataset=legacy. PK, code, геометрия, текущий статус и связи не меняются. Уникальность code теперь действует внутри набора, чтобы старое и новое место с одинаковым code могли безопасно сосуществовать.
3. transition --dry-run только проверяет файл/БД/связи и выводит совпадающие code. Совпадение никогда не считается доказательством одного места.
4. transition с --backup создаёт полную копию, повторяет проверки, ставит старым местам is_active=False и создаёт отдельные canonical-v1 с новыми PK и неизвестным статусом. Старую историю и статистику не переносит и не удаляет. Пользователей, документы и другие таблицы не изменяет. При связанном с ParkingSpot неизвестном типе данных (например, объявлении/брони) операция блокируется до отдельного решения. В текущих моделях таких объявлений/броней нет.
5. import --dry-run проверяет обычное обновление; import без флага идемпотентно обновляет тот же новый набор. При активных legacy обычный импорт блокируется и требует отдельного перехода.

После проверки GET /api/spots/ (734 места, 66 зон) и пробной отметки снова запустите сервер. Шаблон уже включает загрузку мест по API; не развёртывайте его поверх неперенесённой базы без остановки обслуживания: до импорта карта покажет явную ошибку/пустой набор.

Переход и автоматическое резервное копирование поддерживают SQLite, как в текущем settings.py. Для другой СУБД команда применения остановится: нужен отдельный backup/restore-процесс. Перед откатом остановите записи и восстановите **полную** подходящую резервную копию вместе с соответствующей версией кода; частично копировать таблицы мест нельзя. Старые записи остаются в той же БД под dataset=legacy (отдельное пространство записей) и в полной копии; решение об их дальнейшей судьбе не принято.
