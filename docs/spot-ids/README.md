## Сопоставление и пределы уверенности

434 пары подтверждены консервативной геометрической проверкой. 300 мест в 43 рядах требуют просмотра. **Полной подтверждённой таблицы соответствий нет. Не запускайте перенос рабочей базы и полный импорт этого файла.**

`matching-review.json` содержит все 734 предложения, статус каждого, центр `[longitude, latitude]`, три кандидата, расстояние в метрах, IoU (площадь пересечения / площадь объединения), запас стоимости до альтернативы и SHA256 исходной геометрии. `frontend-baseline.json` фиксирует исходную геометрию и ключи Ани. `code-map-confirmed.csv` содержит только 434 подтверждённые пары; это неполная таблица, не план автоматического развёртывания.

Алгоритм использует плоскую метровую проекцию района (как фронтенд), стоимость `distance + 3*(1-IoU)` и глобальную взаимно однозначную задачу назначения. Порядок GeoJSON не используется для выбора пары. `spot-N` в отчёте означает лишь code, который назначал прежний импорт именно этого исходного файла; реальная база может отличаться, поэтому перенос сверяет SHA256 геометрии каждой записи.

Пара считается пригодной только при расстоянии ≤1.5 м, IoU ≥0.4 и преимуществе над альтернативой ≥1 единицы стоимости. Если хотя бы одна пара ряда не проходит, весь этот ряд уходит на проверку. Неопределённость также распространяется на соседние ряды с кандидатами ближе 2 м. Это намеренно оставляет для человека даже часть визуально очевидных соответствий. Соседи и положение в ряду показаны в отчёте; алгоритм не объявляет принудительное назначение доказанным. Например, `spot-174 → z16:16` на 31.288 м — неприемлемая вынужденная пара, а не подтверждённое соответствие.

Откройте `review.html` в браузере (интернет не нужен). Синие фигуры — GeoJSON с прежними spot-N, оранжевые — сгенерированные места с ключами Ани. Выбор ряда показывает его соседей, координаты и кандидатов. Никакая геометрия ради совпадения ID не изменена.

Для решения спорных рядов нужен ответ в виде `spot-N → zX:K` либо указание «у этого полигона нет соответствующего места фронтенда» / «это лишнее место фронтенда». В последнем случае нужно отдельно решить расхождение наборов, а не принуждать биекцию. Ряды с пространственными расхождениями: в первую очередь 22 (z16), 76 (z34), 81 (z38); точные номера выбираются в review.html. Все решения следует проверить на уникальность вместе с остальными парами. Новому физическому месту назначайте новый UUID; не используйте старые удалённые ID.

## Формат фронтенда и localStorage

У каждого ряда `properties.spotIds` — явный массив ID по геометрическим позициям ряда. baseFeats копирует ID, сохранённые в каждом кортеже RUNS (элемент r[7]); ID больше не собирается из зоны и индекса. При перестановке рядов и смене зоны сохраняйте spotIds. При вставке места вставьте новый UUID в соответствующую позицию массива ID; при удалении уберите только ID удалённого места. Нельзя пересобирать весь массив ID по номерам. Изменение числа мест без обновления массива отклоняется. Реестр всех исходных ID — frontend-baseline.json и история RUNS; удалённые значения остаются зарезервированными в истории и не назначаются снова. Новые ID рекомендуется делать UUID без названия зоны.

`me_map_v2` не очищается. Для старого ряда без spotIds ID переносятся только при точном совпадении определения ряда с исходным (геометрия, число мест, тип, угол, шаг, глубина). Название и зона могут отличаться: они не определяют ID. Для изменённого старого ряда создаются постоянные `local:<UUID>`; они сохраняются, внешний вид остаётся прежним, отправка на сервер запрещена до отдельного сопоставления. Исходное значение сохраняется в `me_map_v2_before_ids`. При ошибке localStorage остаётся нетронутым, выводится предупреждение, отображается базовая разметка. Для редактирования геометрии и разделения рядов необходимо переносить spotIds явно. Редактора рядов в актуальном репозитории нет.
